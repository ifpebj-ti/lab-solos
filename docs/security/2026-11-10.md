# Correção dos alertas de segurança e qualidade — 10/11/2026

Entrega rastreada pela [issue #457](https://github.com/ifpebj-ti/lab-solos/issues/457), iniciada em `origin/develop` no commit `c642854c44ff36709e75aeb3f25a3d865640eb8c`.

## Diagnóstico

A consulta autenticada ao GitHub identificou sete alertas Dependabot abertos: quatro altos e três moderados. A consulta CodeQL precisa informar `ref=refs/heads/develop`: nessa branch havia 31 achados, sendo um de segurança alta, quatro de segurança moderada e 26 de qualidade. A consulta sem referência retornava apenas a situação de `main` e não apresentava esses achados.

## Dependências corrigidas

| Dependência no lockfile | Antes | Depois | Referência |
| --- | --- | --- | --- |
| `follow-redirects` | 1.16.0 | 1.16.3 | Dependabot #160, #161 e #166 |
| `zod` | 4.4.3 | 4.6.7 | Dependabot #165 |
| `vite` | 6.4.3 | 6.4.6 | Dependabot #164 |
| `vitest` / `@vitest/mocker` | 4.1.11 | 4.1.12 | Dependabot #162 e #163 |
| `minimatch` usado pelo parser TypeScript | 10.2.6 | 11.0.6 | GHSA-g3hv-75wg-m249, identificado pela auditoria npm |

O `minimatch` recebe um override restrito a `@typescript-eslint/typescript-estree`, pois a versão mais recente do parser ainda declara a versão vulnerável. As demais árvores de dependências mantêm suas versões. A API `minimatch(path, pattern, { dot: true })` usada pelo parser continua disponível, e a versão corrigida aceita o Node 20 usado pela CI. O lockfile registra também a atualização compatível do `typescript-eslint`.

## Imagens e SDK .NET

A primeira pipeline do PR encontrou a vulnerabilidade alta **CVE-2026-111497 / GHSA-p3jp-9v83-76w9**, no decodificador Brotli do runtime 8.0.32, em ambas as arquiteturas do backend. O runtime da API passa a usar **8.0.34-noble-chiseled-extra**, preservando usuário não root, ICU e fusos horários. O utilitário E2E também recebe o runtime 8.0.34. Os digests multiarch foram consultados no Microsoft Container Registry em 10/11/2026.

O SDK passa a **8.0.428**, versão estável registrada nos metadados oficiais do .NET 8 nesta data, sincronizada entre `global.json`, Dockerfiles, CI e contratos de teste. A primeira execução dos dois E2E falhou por segmentation fault no `dotnet restore` do SDK anterior, antes de iniciar a aplicação. A validação das imagens atualizadas fica registrada na pipeline do PR.

O job que compara a baseline instala também o SDK 8.0.419, exclusivamente para reproduzir a coleta da base confiável, cujo `global.json` ainda exige essa versão. O código da entrega é compilado com 8.0.428; os limites da baseline e as regras de segurança não foram alterados.

## Achados CodeQL tratados

| Alertas | Regra / problema | Correção |
| --- | --- | --- |
| #6, #7, #8, #9 | Identificadores controláveis em URLs de produtos e empréstimos | Reutilizar `parseResourceId`, que aceita somente inteiros positivos Int32, antes de montar as URLs. Estender a proteção às mutações e ao identificador de aprovador. |
| #14 | Validação do corpo antecedia a consulta da identidade em notificações | Consultar primeiro a identidade autenticada, mantendo a verificação de acesso por notificação no serviço. |
| #38, #67–#71 | Capturas genéricas de todas as exceções | Tratar explicitamente falhas operacionais de banco, SMTP, criptografia, timeout e cancelamento conforme cada fronteira; permitir a propagação de erros de programação. Preservar logs sem payloads secretos. |
| #63, #64 | Condições complexas | Expressar os contratos do payload de recuperação e das operações JSON Patch com `switch`, preservando os casos aceitos e recusados. |
| #72–#75 | Filtragem implícita em laços | Filtrar nós JSON explicitamente e separar a leitura sequencial dos buckets da filtragem LINQ. As consultas continuam na mesma transação e conexão, sem paralelismo. |
| #77–#82, #88–#90 | `Path.Combine` nos caminhos sintéticos de testes | Usar `Path.Join` para compor os caminhos sem descartar componentes anteriores. |
| #62 | Escrita de estado estático em método de instância de teste | Concentrar o incremento atômico em método estático. |
| #54 | Conversão redundante de `null` em teste | Usar o valor padrão tipado no retorno simulado. |
| #50 | Resultado de consulta atribuído e nunca lido | Remover a atribuição, preservando a execução da consulta existente. |
| #45, #51 | Achados no código produzido pelo gerador de regex do seed | Usar regex estática, com timeout e `NonBacktracking`, para a validação pontual do utilitário; dispensar o código gerado. |

As regras e a configuração do CodeQL permanecem habilitadas. Nenhum alerta foi encerrado manualmente ou dispensado como falso positivo.

## Validação

- A auditoria npm inicial apresentou 12 entradas afetadas, incluindo dependências transitivas. Após a atualização, `npm audit --json` retornou zero vulnerabilidades em todas as severidades.
- `dotnet restore backend/backend.sln --locked-mode` passou. A auditoria NuGet com dependências transitivas não encontrou pacotes vulneráveis.
- O novo teste de notificações falhou antes da correção para corpo sem IDs ou com lista vazia, pois recebia 400 antes da verificação de identidade. A correção exige 401 para o usuário sem identidade em todos os casos.
- Os 18 testes novos de identificadores verificam rejeição antes de qualquer chamada HTTP, segmentos numéricos válidos e cookie de aprovador adulterado.
- Suíte completa do frontend: **150 arquivos e 870 testes aprovados**, tanto na CI quanto na repetição local com `--maxWorkers=2`. Lint e build também passaram. A primeira execução local foi interrompida após timeouts sob pressão de memória.
- Suíte completa do backend: **438 testes aprovados**, incluindo PostgreSQL. A verificação final de notificações e segurança do seed aprovou mais uma execução dos 36 casos selecionados.
- A primeira análise do PR confirmou **zero achados de CodeQL em C# e JavaScript/TypeScript**, em comparação aos 31 da base. A situação da pipeline após a atualização das imagens é registrada no PR vinculado à issue.

Os alertas do GitHub só refletem o código corrigido depois da análise da referência correspondente e da integração. O PR para `develop` não atualiza automaticamente `main` nem publica uma release; a promoção estável continua pela esteira do projeto.
