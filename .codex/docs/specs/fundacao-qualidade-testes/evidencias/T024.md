## Escopo entregue

O Playwright foi dividido nos projetos `real` e `ui`. Os casos reais ficaram
em `credential-lifecycle.spec.ts`, `user-data-contract.real.spec.ts` e
`infra/smoke.e2e.ts`; os demais continuam no projeto UI com mocks. O projeto
real usa `fullyParallel: false`, `workers: 1` e `retries: 0`. A listagem
preservou todos os casos existentes e passou a expor o filtro `credenciais`.

O helper `frontend/e2e/infra/e2e-data.ts` deriva a conta do cenario de
`E2E_SEED_SCENARIO`, usa `E2E_COMPOSE_PROJECT`, aceita portas externas da stack
por ambiente e prepara os registros com o servico `e2e-seed` do T023. A
recuperacao identifica mensagens novas por destinatario no Mailpit e nao
limpa a caixa global. Nenhuma jornada real usa `route.fulfill`.

## RED / GREEN / REFACTOR

- RED: a configuracao anterior tinha apenas o projeto `chromium`, usava a
  conta administrativa global e apagava a caixa do Mailpit; a execucao real
  revelou ainda a divergencia de contrato no reset de senha.
- GREEN: a classificacao, o helper de cenario, o filtro de credenciais, o
  ciclo real completo e toda a suite UI passaram. A correcao autorizada mapeia
  o campo interno `token` para `code` no contrato HTTP real de reset.
- REFACTOR: os casos de dados foram separados entre UI e API/navegador real;
  as credenciais e portas passaram a ser derivadas do cenario e o caso de
  troca tambem verifica a revogacao de duas sessoes.

## Correcao QC-005 autorizada

Por autorizacao explicita do solicitante para destravar as tarefas restantes,
`frontend/src/integration/Auth.ts` passou a enviar `code: data.token` para
`/api/Email/reset-password`, preservando `token` apenas na interface interna
usada pela pagina. Os testes de `ResetPassword` foram ajustados para verificar
o contrato de rede sem expor credenciais.

## Achado e resolucao QC-005

O caso real de recuperacao solicitou o reset pela interface, localizou no
Mailpit a mensagem do destinatario `synthetic-admin-t024@example.invalid` e
extraiu o token vigente. O POST real retornou 400 porque
`frontend/src/integration/Auth.ts` envia o campo `token` para
`/api/Email/reset-password`, enquanto o contrato real de
`PasswordResetDTO`/`EmailController` exige o campo `code`. A comparacao do
hash do token com o registro do banco e a validade temporal foram verificadas
sem imprimir o token.

O ajuste foi autorizado explicitamente nesta execucao, aplicado no frontend e
validado novamente por UI, API, banco e Mailpit: o filtro de credenciais passou
4/4 e a suite real passou 7/7. Nao foi usado mock para esconder a falha e nao
houve commit, push, merge, PR ou fechamento da issue.
